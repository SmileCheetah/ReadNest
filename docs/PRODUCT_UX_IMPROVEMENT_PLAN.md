## 1. 문서 우선순위와 제품 목표

현재 제품 방향·작업 우선순위는 이 문서, 단일 Markdown 요약의 현행 계약은 [RICH_MARKDOWN_SUMMARY_PLAN.md](RICH_MARKDOWN_SUMMARY_PLAN.md)를 기준으로 한다. 이 문서의 **제안**은 구현 완료나 배포 완료를 뜻하지 않는다. 구현 시 해당 작업의 계약·테스트·검증 커밋을 갱신한다.

기존 `WORKING_NOTES`, `SUMMARY_DETAIL_UI_IMPLEMENTATION_PLAN`, `ROADMAP_AND_RELEASE_CRITERIA`, `WORK_STATUS_SUMMARY`, `REMAINING_WORK`, `MVP_PLAN`, `THREAD_COLLECTION_PLAN`은 과거 설계·이력이다. 그 안의 V1 fallback, 3개 포인트 고정, Gemini, 웹 프론트 지침을 현재 구현에 재도입하지 않는다.

**제품 목표:** 저장한 글의 핵심을 빠르게 떠올리고, 필요할 때 원문으로 돌아갈 수 있게 한다.

- ‘10초’는 주제와 핵심 주장을 알아보는 시간이다. 모든 독립 항목을 10초에 읽도록 내용을 버리는 목표가 아니다.
- 상세 본문은 `summaryMeta.summaryMarkdown` 하나다. V1/V2 화면 분기나 실패 시 옛 요약 UI를 복원하지 않는다.
- 독립적인 주장·조건·비교·수치·주의사항을 보존한다. 반복만 합치고 항목 수를 강제하지 않는다.
- 항목별 1~2문장은 가독성을 위한 소프트 가이드다. 의미를 훼손하는 글자 수·비율·문장 수 강제 검증은 하지 않는다.
- 사용자가 왜 저장했는지는 모델이 추측하지 않는다. ‘다시 볼 글’도 관심사를 안다는 식으로 설명하지 않는다.
- 이번에는 프롬프트를 다시 바꾸기보다 입력 원문, 처리 상태, 화면 표시가 올바른지 먼저 고친다.

## 4. 디자인 감사와 개선안

### 4.1 감사 결과

`ss-audit`의 상태 가시성·사용자 통제·오류 복구·최소 표현·모바일 접근성 관점으로 코드와 제공된 과거 화면을 검토했다. **잠정 C+**이며 실기기 사용성 평가 점수가 아니다.

| 항목 | 잠정 평가 | 이유 |
| --- | --- | --- |
| 상태 가시성/오류 복구 | C | 생성 완료 추적 누락, 원인을 구분하지 못하는 실패, 조회 실패 미노출 |
| 사용자 통제 | C | 수동 안 읽음과 자동 읽음 충돌, 성공 글 재요약 액션 부족 |
| 문서 읽기 구조 | B- | 단일 문서로 개선됐지만 중간 block 접기와 줄바꿈 회귀 위험 |
| 다시 찾기/정보 위계 | C | 홈 중복, 제목 중심 보관함, 미리보기 데이터 부적합 |
| 접근성 | C / 실기 미검증 | 목록/메뉴 그룹 읽기, 복사 알림, 작은 필터 영역·저대비 텍스트 보완 필요 |

**중대:** 완료 상태 미반영·수동 의도 취소·내용 건너뛰기. **주요:** 미리보기, 필터/오류, 목록 접근성. **경미:** 영어/한국어 라벨 혼용, 과한 배지와 반복 여백. 새 폰트만 적용해서 해결할 문제가 아니다.

### 4.2 홈 — 저장 입력 중심에서 다시 읽기 중심으로

- 상단: `Unwind` + `링크 저장` 버튼. 버튼은 입력 패널을 열고, 첫 사용자에게는 입력 안내를 바로 표시한다.
- 첫 콘텐츠: `다시 볼 글`. 기존 읽음 상태와 저장 시각으로 설명 가능한 정렬만 사용한다.
- 처리 중인 글이 있을 때만 얇은 `요약 중 N개` 상태 영역. 실패는 별도 복구 액션과 표시한다.
- 동일 글을 여러 섹션에 반복하지 않는다. 최근 저장과 다시 볼 글을 나누면 ID 기준 제외 규칙을 둔다.
- 카드: 제목 2줄 + **동일 Markdown에서 추출한** 핵심 preview 1~2줄 + 출처/저장일. 정상 완료 배지는 생략하고 진행/실패만 강조한다.
- 현재 데이터가 1~2개여도 ‘이 3개’라고 표시하는 하드코딩 제거. 비어 있으면 저장 행동 안내 하나만 제공한다.

### 4.3 상세 — 하나의 읽기 좋은 문서 유지

```text
←                                          ⋯
Threads · 저장일
제목 — 한 번만 표시

핵심 도입 문단 — 본문과 같은 글, 중복 표시 안 함

[원문 보기 ↗]                       [복사]

소제목
짧은 설명 / 필요한 목록 / 선택적 인용 강조
... 독립 핵심 항목은 모두 유지 ...

한 줄 요약
굵은 핵심 메시지

원문 수집 정보 ▾   (확인 가능한 정보가 있을 때만)
```

- H1은 화면 제목으로 한 번만 표시한다. H1이 없으면 저장 제목을 사용한다. 본문은 저장된 순서와 의미를 유지한다.
- 기본은 전체 문서를 펼친다. 매우 긴 문서만 의미 단위 경계에서 접고 `전체 요약 펼치기` 제공. 첫 의미 단위가 긴 경우 그 단위는 보여 주며, 제목만 남기는 접기를 금지한다.
- ‘분석 정보’를 단순히 ‘핵심 요약’으로 이름만 바꾸지 않는다. 현재 내용은 요약이 아니라 상태값이고 일부 값은 고정되어 있다.
- **한눈에 보기 제안:** 먼저 도입부의 위계와 간격만 개선한다. 별도 축약이 필요하다는 사용성 증거가 나오면 같은 문서의 명시적 한 줄 요약을 재배치하는 안을 비교한다. 새로운 모델 호출이나 두 번째 요약 필드는 우선 추가하지 않는다.
- 재배치 시 원문 Markdown의 표시 block만 나눈다. 제목/도입/마지막 한 줄을 두 번 렌더링하지 않고 복사·공유는 원 Markdown 전체 + 원문 URL을 유지한다.
- `원문 보기`는 유일한 주요 CTA, 복사는 보조 액션. 위험한 삭제는 더보기→대상 확인→삭제 흐름을 유지한다. 즉시 삭제인데 ‘실행 취소’를 약속하지 않는다.
- 성공한 글의 재요약은 더보기에서 명시적으로 요청하게 한다. 실행 중 중복 요청을 막고, 조회 새로고침과 재요약을 구분한다.
- 부분 수집 경고는 본문을 읽기 **전**에 표시한다. 확인되지 않은 ‘완결/신뢰도’는 숨기거나 `확인하지 못함`으로 표시한다.
- 현재 코드에 없는 플로팅 설정 버튼은 앱 요소라고 단정하지 않는다. 실행 기기에서 오버레이 출처와 실제 배포 버전을 확인한다.

### 4.4 보관함 — 저장한 글을 다시 찾을 수 있게

- 기본 범위 `전체 저장글`, 검색 + 읽음 필터, 기간은 보조 필터로 제공한다.
- `월별 아카이브`는 실제 월별 이동 구현 전에는 `전체 기간`으로 수정한다.
- 제목 2줄, 핵심 preview 1~2줄, 저장일 중심. 짧은 제목만으로 내용을 추측하게 하지 않는다.
- 로딩/저장글 없음/검색 결과 없음/네트워크 실패를 별도 표시한다. 조회 실패에 `다시 불러오기`를 제공한다.
- Backend cursor 도입과 함께 가상화 목록 적용. 상세에서 돌아오면 검색 조건·스크롤 위치를 유지한다.

### 4.5 타이포그래피·토큰·접근성

- 기존 Unwind 파란색 `#0075de`, 산세리프, 둥근 형태를 유지한다. 본문은 평면 문서, 목록 카드만 약한 경계로 구분한다.
- 제목 24~28 / 700, 섹션 18~20 / 700, 본문 16 / 행간 26~28, 보조 정보 13 / 행간 20을 초기 시안으로 비교한다. 문서 h2/h3의 의미 계층은 유지한다.
- 문단 14~18, 섹션 28~32, 본문 좌우 20~24 간격. 320px/200%에서는 실제 가용 폭에 맞추고 고정 높이로 자르지 않는다.
- 인용문은 짧은 왼쪽 accent **또는** 약한 배경 하나만 사용. 본문 전체/모든 번호를 파랗게 강조하지 않는다.
- 모든 액션 최소 44×44, 주요 액션 48 이상 목표, 액션 사이 8 이상. 필터·아이콘·접기 버튼 포함.
- 작은 텍스트 대비 4.5:1을 검증 기준으로 사용한다. 현재 주황 배지 약 2.15:1, 희미한 회색 날짜/흰 배경 약 3.36:1은 개선 대상이다.
- 목록의 부모 `accessible`이 항목을 묶어 숨기는지 실기 확인 후 조정. 번호·제목·본문 순서, heading 역할, 탭 선택/펼침 상태, 모달 진입·복귀 포커스를 검증한다.
- 복사 완료 2초 표시와 스크린리더 알림, 실패 시 다시 복사 안내. 긴 기술 용어·두 자리 번호·확대된 하단 탭이 본문을 가리지 않게 한다.

## 5. 핵심 설계 결정

### D1. 요약 형식과 길이

**문제 →** 같은 글도 과도하게 길거나 짧아지고 프롬프트 변경만 반복했다. **선택지 →** 고정 항목 수/글자 수, 추가 축약 모델, 단일 본문 + 품질 평가. **선택 →** 단일 Markdown 유지와 입력·평가·표시 개선 우선. **이유 →** 독립 핵심을 버리지 않고 현재 문제의 원인을 분리할 수 있다. **트레이드오프 →** 글마다 길이는 달라지고 사람이 의미 보존을 평가해야 한다.

### D2. 빠른 미리보기

**문제 →** 현재 `oneLineSummary`가 H1이며 목록은 전체 Markdown을 잘라 보여 준다. **선택지 →** 별도 AI 호출, 기존 필드 맹목 재사용, 같은 본문에서 추출. **선택 →** 제목을 제외한 첫 실제 문단을 기본 preview로 추출하고, 명시적 한 줄 요약이 있으면 목록용 후보로 비교. **이유 →** 추가 비용·서로 다른 요약의 의미 불일치가 없다. **트레이드오프 →** 모든 글에 매우 짧은 preview를 보장하지 못한다. 목록 말줄임은 표시만 제한하고 저장 본문은 자르지 않는다.

### D3. 처리 정합성

**문제 →** DB/Redis/외부 AI가 분리되어 중복과 정체가 생길 수 있다. **선택지 →** 재시도만 추가, 긴 DB 트랜잭션, DB 작업 레코드+generation. **선택 →** 복구 가능한 작업 레코드와 dispatcher, 조건부 결과 저장. **이유 →** DB에서 수락한 작업을 다시 발견할 수 있고 오래된 결과를 차단한다. **트레이드오프 →** migration과 운영 복구 로직이 필요하다. 네트워크 호출까지 DB 트랜잭션에 넣지 않는다.

### D4. 읽음 정책

**문제 →** 진입 자체를 읽음으로 만들고 수동 안 읽음도 덮는다. **선택지 →** 진입 즉시/스크롤 완료/유효한 요약 노출. **선택 제안 →** 유효한 요약이 처음 표시된 진입 세션에서 자동 READ 최대 1회. 수동 UNREAD/READ_LATER는 그 세션에서 우선한다. **이유 →** 생성 실패 화면 방문은 읽기가 아니며 사용자 선택이 우선이다. **트레이드오프 →** READ는 이해 완료를 증명하지 못하므로 회상 성과와 별도로 측정한다.

늦은 응답을 무시하는 것만으로 서버 저장 순서까지 보장하지 못한다. 단계 1에서 글별 PATCH를 직렬화하고 마지막 사용자 의도를 적용한다. 전송 결과가 불확실하면 서버 조회와 재적용으로 조정하며, 다중 기기의 동시 수정까지 지원할 때는 revision/CAS 계약으로 확장한다.

## 6. API·데이터·상태 설계 초안

아래는 후속 구현 계약의 초안이다. 현재 API가 이미 이 필드를 제공한다고 가정하지 않는다.

### 6.1 단계적으로 적용할 계약

| 영역 | 1차: 현행 계약에서 수정 | 후속: 추가 계약 |
| --- | --- | --- |
| 요약 본문 | `summaryMeta.summaryMarkdown` 하나 유지, validator fixture 일치 | 새 요약 본문/버전 필드 추가 없음 |
| 상태 조회 | 기존 상세/status GET으로 진행 상태 추적, 완료 시 상세 갱신 | `generation`, `stage`, `retryable`, `retryAfterSeconds`, 안전한 `errorCode` 추가 |
| 원문 | 빈 수집 gate, 새 스냅샷으로 교체, 거짓 완결 제거 | `sourcePostId`, `authorId`, 수집 시각, 확인한 parts/expected/missing, `UNKNOWN/PARTIAL/COMPLETE` |
| 목록 | 클라이언트에서 안전한 preview를 추출 | 경량 `summaryPreview`, `(savedAt,id)` cursor, `{ items, nextCursor }` opt-in 응답 |
| 재요약 | 현재 소유자 확인 유지, 중복 누름/동시 실행 방지 | 동일 generation 재요청은 기존 작업 반환, 새 생성은 명시적 사용자 액션 |
| 읽음 | 기존 PATCH 유지, 글별 요청 직렬화·마지막 의도 적용, GET/poll 병합 보호 | 다중 기기까지 필요하면 수정 버전 기반 조건부 갱신 검토 |

목록 응답은 기존 배열을 즉시 객체로 바꾸지 않는다. 예: `pagination=cursor`로 새 DTO를 opt-in하여 구 앱 호환을 유지한다. 상세 API에는 전체 Markdown을 유지하고 목록에서는 rawText/LONGTEXT를 제외한다. 계정/필터를 포함한 cursor를 검증하고 안정적 정렬을 사용한다.

### 6.2 상태와 사용자 안내

| 상황 | 저장/화면 원칙 | 복구 |
| --- | --- | --- |
| 수락/수집/생성/저장 중 | 기존 `SUMMARIZING` 유지, 내부 stage 구분. 완성 요약처럼 보이는 가짜 문구 금지 | 조회만 재개, 조회 timeout으로 생성 실패를 확정하지 않음 |
| 정상 완료 | 현재 generation 결과만 저장·표시 | 복사/원문/읽음 제공 |
| 정상 글 재요약 중/실패 | 마지막 성공 Markdown을 보존하고 ‘이전 요약·새 요약 생성 중/갱신 실패’ 안내 | 최신 generation 성공 시 한 문서를 원자 교체. 기존 결과가 없을 때만 빈/실패 화면 |
| 부분 원문 | 수집 증거가 있을 때 부분 경고, 요약할 본문이 있으면 제한을 밝힘 | 원문 보기/명시적 재수집 |
| 빈 원문/로그인 벽 | AI 호출 전 실패, 예: `EXTRACTION_FAILED` | 접근 가능한 원문 확인, 허용된 원문 입력 경로 검토 |
| 공급자 429/timeout/5xx | 일시 오류로 분류, 안전한 메시지 | 제한된 backoff+jitter, 실제 retry-after 존중 |
| 영구 인증/입력/형식 오류 | 무의미한 자동 재시도 금지 | 사용자 입력 수정 또는 운영 조치 |
| DB 저장 실패 | 완료로 보고하지 않음, 생성 결과 재사용 가능성 검토 | 저장 단계 복구, 모델을 무조건 다시 호출하지 않음 |
| 연속 글 감지 실패 | 정상 요약 결과 유지, 부가 경고 기록 | 부가 작업 별도 재실행 |
| 모바일 offline/조회 오류 | 생성 실패와 구분, 마지막 확인 상태 표시. 네트워크 오류만으로 저장된 토큰 삭제 금지 | 연결 복귀 시 조회 재개. 인증 거부/폐기가 확인된 경우에만 로그인 요구 |

재요약의 마지막 정상 결과 보존은 **후속 제안**이며 옛 V1 fallback이 아니다. 현행 진행 중 본문 숨김 정책과 다르므로 구현 시 요약 계약 문서도 함께 갱신한다. 한 화면에는 같은 Markdown 문서 하나만 표시하고, `generation`과 별도로 `resultGeneration`/생성 시각을 기록해 이전 결과임을 구분한다.

서버 error 응답은 SQL·내부 주소·키를 노출하지 않는다. 기존 재시도 3회는 영구 누적인데 ‘잠시 후’라고 안내하므로, 실패 유형별 재시도/대기 시간을 구현과 함께 일치시킨다. 새 retry 예산의 값과 시간창은 실제 실패·비용 측정 후 정하고 무제한으로 풀지 않는다.

### 6.3 트랜잭션·멱등성·수집 경계

1. 소유자와 지원 URL을 검증한다. 단계 1에서는 DB 길이 한도 초과를 저장 전에 명확히 거부한다. URL 자체를 191자로 절단하지 않는다. 단계 2에서는 Threads post 식별자 기준으로 정규화하고 출처가 다른 URL은 함부로 합치지 않는다. 기존 중복 데이터는 dry-run과 보존 정책 없이 병합/삭제하지 않는다.
2. DB 트랜잭션에서 현재 generation 증가와 작업 레코드 생성을 함께 기록한다. 사용자/작업 멱등 키에 unique 제약을 둔다. 중복 저장은 기존 글을 반환하고 본문을 초기화하지 않는다.
3. dispatcher가 미전송 레코드를 BullMQ에 같은 job ID로 전달한다. Redis 장애 후에도 재전송할 수 있어야 한다.
4. worker는 DB 조건부 claim/lease로 작업 소유권을 획득한다. 자동 재시도와 새 재요약 generation을 구분한다.
5. 수집/AI 호출은 DB 트랜잭션 밖에서 수행한다. 원문 누적 금지, timeout/크기/동시 브라우저 수 예산 적용. 부분 수집을 길이만으로 ‘완결’ 판정하지 않는다.
6. 성공·실패 저장 모두 현재 generation/lease/삭제 여부를 검사한다. 이전 worker는 결과를 덮거나 삭제된 글을 되살릴 수 없다.
7. 사용자 quota도 count→create 경쟁을 고려한다. 중복 요청은 신규 저장 quota를 소비하지 않게 하고 날짜 기준 timezone을 명시한다.

이는 **at-least-once 전달 + 멱등 저장** 설계다. AI 응답 직후 프로세스가 죽으면 중복 호출 비용까지 완벽히 없어진다고 약속하지 않는다. 단계별 checkpoint/결과 재사용과 계측으로 완화한다.

연속 글의 COMPLETE는 마지막 번호 발견만으로 확정하지 않는다. 같은 작성자/루트 게시물, 기대 개수, 전체 인덱스 집합의 누락 없음이 확인돼야 한다. 확인 불가하면 UNKNOWN, 일부 누락 증거가 있으면 PARTIAL. 모델이 만든 제목으로 글 묶음 identity를 정하지 않는다.

## 7. 작업 분해와 순서

| 단계 | Frontend | Backend | 완료 게이트 |
| --- | --- | --- | --- |
| 0. 기준 정리 — 이번 작업 | 디자인 감사/현행 화면 확인 | 코드·계약 감사 | 문서 충돌 표시, 테스트 baseline, 계획 커밋 |
| 1. 즉시 신뢰성 수정 | FE-01~05, API-01. 상태 추적·읽음·접기·늦은 응답·오프라인 회귀 | BE-01~04, BE-07. URL 제한·원문 교체·부가 실패 격리·빈 원문/입력 길이 gate | 관련 회귀 테스트 + 실제 격리 환경의 저장→표시 1회. 운영 호출/배포와 분리 |
| 2. 작업 정합성 | generation별 상태 추적, 중복 재시도 disabled/복구 안내 | BE-05~06, 작업 레코드/dispatcher/CAS·정규화·quota/재시도 정책 | MySQL/Redis 통합 장애·동시성·소유권 테스트, migration 전후 구 앱 호환 |
| 3. 읽기·회상 디자인 | 홈/상세/보관함 재구성, preview·토큰·접근성, 재사용 컴포넌트 | API-02~03, 경량 목록/cursor, 수집 정보 진실성 | 실제 320px·200%·스크린리더, 검색/페이지 이동, 사용자 회상 테스트 |
| 4. 출시 검증 | 설치 빌드에서 링크 수신·복사·공유·네트워크 복구 | 로그/지표/복구 runbook, 빌드·prompt 버전 확인 | 검증 결과와 릴리스 SHA 연결, rollback 절차 |

공개 서비스 출시 게이트에는 API 또는 인프라 계층의 가입·로그인·저장·재요약 rate limit, 사용자별 요청/동시 실행/AI 비용 예산, 429 안내를 포함한다. 현재 코드에서는 endpoint rate limit을 확인하지 못했고 인프라 적용 여부는 미검증이다. 일일 저장 quota만으로 이 요건을 충족했다고 간주하지 않는다.

단계 1의 FE/BE는 Markdown 허용 fixture를 먼저 합의한 뒤 병렬 진행 가능하다. 단계 3의 정적 UI/토큰 시안은 단계 2와 병렬 가능하지만 신규 상태·목록 계약 연결은 Backend 완료 후 진행한다. 대규모 App.tsx 재작성과 기능 변경을 한 PR에 섞지 않는다.

### 변경 예정 파일/컴포넌트 경계

- Frontend: `App.tsx`의 요청·목록 상태를 기능 단위 hook으로 분리, `ThreadDetailScreen`, `MarkdownSummary`, `ThreadCard`, `StatusBadge`, `BottomNav`, `theme/tokens`, `api/readnestApi`, `api/articleMapper` 및 각 테스트.
- 재사용 단위 제안: `ArticlePreview`(같은 문서의 텍스트 추출), `SummaryStatus`(진행/오류/재시도), `SummaryDocument`(제목/본문 의미 구조), 상태 추적 hook. 각 화면 전용 카드 시스템이나 새로운 전역 상태 라이브러리부터 만들지 않는다.

## 8. 테스트와 성공 조건

### 자동 검증

- 새 저장이 2.5초 이후 또는 40초 이후 완료되어도 조회를 재개하면 표시된다. 앱 background/logout/다른 글 이동 시 이전 polling이 화면을 변경하지 않는다.
- 유효한 요약 첫 노출만 자동 READ. 수동 UNREAD/READ_LATER 유지, 늦은 GET/poll/실패 rollback은 최신 의도를 덮지 않는다.
- Markdown: 번호 원본, h1~h3, bold, 목록, quote, soft/hard break, 한글/C++/CUDA/긴 영문, 문장 속 `|`, 위험 문법. FE/BE가 같은 fixture를 허용/거부한다.
- 긴 중간 block/첫 block/heading만 있는 입력: 접힌 화면은 연속된 의미 단위이며 중간 누락 후 결론 노출이 없다. 복사/공유는 전체 원문 Markdown을 유지한다.
- 재요약 반복 시 같은 원문이 누적되지 않는다. 수집 실패 시 모델 미호출. 부가 감지 실패 시 완료 결과 유지. 재요약 실패는 마지막 정상 문서를 손상시키지 않는다. 제목 191/192/200자·이모지와 긴 공유 URL/추적 파라미터 경계 검증.
- 오프라인 세션 복원은 토큰을 삭제하지 않고 재시도할 수 있다. 인증 폐기와 연결 오류를 구분한다. 읽음 PATCH 서버 반영 순서·재접속 후 상태를 검증한다.
- 동시 저장/재요약, enqueue 실패, worker 종료·재기동, 오래된 worker, 삭제 중 완료, 계정 간 조회/수정, 제한 초과와 재시도 정책을 MySQL/Redis 격리 환경에서 검증한다.
- 페이지 경계 중복/누락, 같은 savedAt, filter 변경, 100개 초과 데이터, timezone 경계. 목록 payload와 쿼리 수/실행 계획을 측정한다.

### 실제 화면·품질 검증

- 320px, 기본/200% 글자 크기, Android TalkBack/iOS VoiceOver: 터치 영역, 번호/본문 순서, 목록·모달 포커스, 복사 알림, 하단 가림 없음.
- 빈/조회 중/진행 중/실패/부분 수집/완료/재시도/오프라인 상태를 모두 캡처하고 빌드 SHA·기기·API 환경을 기록한다.
- 직접 저장한 글 5개씩, 사용자 5명 정도의 초기 테스트: 10초 노출 뒤 주제·핵심 주장 정확 회상 **80% 이상을 목표**로 둔다. 아직 측정된 성과가 아니다.
- 독립 항목/조건/숫자/비교/짧은 단일 주장/부분 수집을 포함한 20개 평가셋 구축. 누락·반대 의미·추가 조언·거짓 확신을 사람이 평가한다. mock fixture 통과와 실제 Luna 품질 평가를 구분한다.
- 실제 모델 호출은 고정 원문·model·prompt 버전·출력·사용량·평가를 함께 보관한다. API 키/사용자 원문을 일반 로그에 남기지 않는다.
- ‘공유 한 번으로 저장’은 현재 딥링크 지원과 같지 않다. Android/iOS share target 설정과 설치 빌드 동작을 별도로 검증한다.

### 운영 측정

최초/재시도 성공률, 수집·모델·검증·저장 단계별 실패율, queue 대기와 각 단계 p50/p95, 처리 정체 수, 중복 실행/오래된 결과 거부 수, 목록 응답 크기·쿼리 수를 먼저 측정한다. 이후 측정값에 맞는 SLO와 retry 예산을 정한다.

제품 지표는 저장 후 7일 내 재방문과 보관함에서 목표 글 찾기 성공률/시간을 본다. 자동 READ나 원문 클릭률만으로 이해/만족을 판단하지 않는다. 진단 정보에는 app/API commit, prompt version, generation을 포함하고 민감한 원문은 제외한다.

## 9. 보류와 릴리스 원칙

- BYOK, Java/Spring Boot 이관, 별도 짧은 AI 요약, 추가 플랫폼 수집, 삭제 복구는 별도 설계/승인이 필요한 후속 후보다. 현재 개선과 한 번에 진행하지 않는다.
- Java 이관 전에 API 계약·상태·회귀 테스트를 확정하면 현재 언어와 무관하게 이전 가능한 백엔드 설계 자산이 된다.
- 문서·커밋·push·서버 재시작·배포·기존 데이터 재요약은 서로 다른 완료 단계다. main 반영이 실행 환경 반영을 뜻하지 않는다.
- 문서 변경은 이번에 커밋/공유한다. 후속 애플리케이션 구현은 별도 시작 요청 후 범위별 구현·전체 diff 리뷰·검증을 거친다.
- 완료 보고는 `코드 구현 / 자동 검사 / 통합 검사 / 실제 모델 / 실기기 / main 반영 / 배포`를 각각 사실대로 적는다. 미검증 상태를 완료로 표시하지 않는다.
