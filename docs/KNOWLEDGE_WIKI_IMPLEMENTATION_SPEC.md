# Threads 지식 Wiki 후속 구현 명세

저장한 글을 주제로 묶고, 출처를 확인할 수 있는 Wiki를 편집하며, 선택한 자료에 질문하는 흐름을 만든다. 기존 글 상세·요약·밀도 선택은 그대로 유지한다. 원문과 AI 종합, 사용자가 작성한 내용을 구분해 다시 찾기와 재사용을 돕는다.

2026-10-07 기준 **1단계 수동 주제·저장글 연결과 원문 근거 기반 자동 글 연결은 구현**, 2·3단계 Wiki·질의응답은 후속 설계다. 자동 연결은 근거가 표시되는 실선 목록이지 자유 배치 그래프나 자동 종합 Wiki가 아니다. GPT-6 Luna 전환과 Obsidian 노트 복사도 유지한다. 상위 계획은 [Threads 지식 Wiki 개선 계획](KNOWLEDGE_WIKI_PLAN.md), 성능 과제는 [요약 지연 개선 계획](SUMMARY_LATENCY_INVESTIGATION.md)을 따른다.

## 제품 흐름과 범위

| 단계 | 사용자의 행동 | 얻는 결과 |
| --- | --- | --- |
| 주제 정리 | ‘AI 업무 활용’ 같은 주제를 만들고 저장글을 연결 | 주제별 읽기 목록과 직접 작성한 설명 |
| Wiki 작성 | 연결된 글 중 사용할 출처를 선택해 초안 생성 | 주장별 출처를 확인하고 편집할 수 있는 초안 |
| 검토와 저장 | AI 초안을 검토하고 명시적으로 적용 | 사용자가 관리하는 Wiki 문서와 변경 이력 |
| 자료에 질문 | 선택한 글을 근거로 질문 | 근거 글과 수집 범위를 보여주는 답변 또는 근거 부족 안내 |

초기에는 수동 주제 분류와 출처 선택을 우선한다. 모든 글 자동 분류, 전체 보관함 의미 검색, 그래프 시각화, 외부 검색, Obsidian Vault 양방향 동기화는 별도 단계다. 질문 화면도 처음에는 ‘내 모든 지식에 질문’이 아니라 **선택한 자료에 질문**으로 표시한다.

주제 하나에 글 여러 개, 글 하나에 주제 여러 개를 허용한다. 주제에 같이 속한다는 것은 사용자가 함께 분류했다는 뜻이며, 저자 간 합의나 내용의 인과관계를 뜻하지 않는다. ‘관련 글’ 역시 처음에는 같은 주제의 글이라는 이유를 표시한다. 임베딩 기반 추천은 정확도와 비용을 검증한 뒤 추가한다.

사용자 주제는 AI가 생성한 `SavedThread.tags`와 별개다. 태그를 수정해서 사용자 분류를 구현하면 재요약 시 사라질 수 있으므로 주제 연결을 별도 저장한다.

## 현재 코드와의 경계

- `SavedArticle.rawText`는 재요약 성공 시 최신 수집 원문으로 교체된다. `resultGeneration`만 참조해서 과거 Wiki의 근거를 재현할 수 없다. 생성 시 사용한 원문 스냅샷이 필요하다.
- `ThreadGroup`과 `ThreadPart`는 같은 Threads 연재의 순서를 나타낸다. 개인 주제 분류나 의미 연결 테이블로 재사용하지 않는다.
- 기존 summary Markdown validator는 일반 Markdown 링크도 거부한다. 기존 요약 검증을 느슨하게 바꾸지 않고 Wiki의 인용 계약을 별도로 둔다.
- `MarkdownSummary`만으로 내부 출처 이동을 구현하지 않는다. 본문과 검증된 출처 참조를 함께 렌더링하는 Wiki 컴포넌트를 추가한다.
- 현재 클라이언트는 홈·보관함·설정과 선택된 글 상세를 관리한다. Wiki → 출처 상세 → Wiki 복귀에는 별도 복귀 대상과 스크롤 상태가 필요하다.
- 기존 목록 검색은 제목·요약·URL 기반이다. 이를 원문 전체 검색이나 의미 검색이라고 표시하지 않는다.
- durable task와 lease 패턴은 참고하되 Wiki 작업을 기존 요약 task·상태에 억지로 넣지 않는다. Wiki 실패가 기본 요약을 실패로 만들면 안 된다.

## 1단계 주제와 저장글 연결

### 화면

보관함 안에 ‘주제’ 진입점을 둔다. 첫 단계부터 하단 탭 전체를 재편하거나 기존 상세 카드를 바꾸지 않는다. 주제 목록에는 이름, 사용자 설명, 연결된 글 수를 표시한다. 글이 없는 사용자는 링크 저장으로, 주제가 없는 사용자는 첫 주제 만들기로 안내한다.

글 상세 더보기의 ‘주제에 추가’에서 기존 주제를 선택하거나 새로 만든다. 주제 상세에서는 글 검색·선택·연결 해제가 가능하다. 연결 해제는 글 삭제가 아니다. 주제 삭제도 그 주제와 연결만 제거하고 원본 저장글은 남긴다. 같은 주제의 글 목록은 AI 추천으로 표시하지 않는다.

### 데이터와 계약

| 모델 | 주요 필드와 제약 |
| --- | --- |
| KnowledgeTopic | id, userId, name, description, revision, createdAt, updatedAt |
| TopicArticle | topicId, articleId, createdAt; topicId와 articleId 조합 unique |

이름 80자·설명 2,000자를 Unicode 코드포인트 단위로 제한하며 제목을 조용히 자르지 않는다. 이름은 NFC와 연속 공백 정규화 후 검사하고, 중복 비교에는 NFKC·소문자화한 이름의 SHA-256 `nameKey`를 사용한다. 비어 있거나 보이지 않는 문자만 있는 이름과 제어 문자를 거부하되 정상 emoji 조합은 허용한다. 같은 사용자의 중복 이름은 409와 기존 주제 ID를 반환한다. 다른 사용자의 동일 이름은 허용한다.

| 구현 API | 의미 |
| --- | --- |
| GET /api/knowledge/topics | 소유자의 주제 목록, cursor pagination |
| POST /api/knowledge/topics | 주제 생성 |
| GET /api/knowledge/topics/:id | 주제와 개수·revision 조회; 본문 목록은 별도 |
| PATCH /api/knowledge/topics/:id | expectedRevision 기반 이름·설명 수정 |
| DELETE /api/knowledge/topics/:id | 주제와 연결 삭제, 저장글 보존 |
| GET /api/knowledge/topics/:id/articles | 주제 안의 글 목록, 검색·cursor pagination |
| PUT /api/knowledge/topics/:id/articles/:articleId | 글 연결; 반복 요청은 동일 결과 |
| DELETE /api/knowledge/topics/:id/articles/:articleId | 연결 해제; 반복 요청은 안전하게 처리 |
| GET /api/knowledge/articles/:articleId/topics | 저장글이 연결된 소유자의 주제 목록, 검색·cursor pagination |

목록 응답은 `items`, `nextCursor`를 사용하며 기본 30개·최대 100개를 반환한다. 주제는 생성 시각·ID 내림차순, 글은 저장 시각·ID 내림차순이다. 서명된 cursor는 소유자·조회 종류·주제/글·검색 조건에 묶어 다른 범위에 재사용하지 못하게 한다. 글 목록은 미리보기만 반환하며 수집 원문·요약 전문·내부 오류 로그는 반환하지 않는다.

주제 DTO는 `id, name, description, revision, articleCount, createdAt, updatedAt`이다. 모든 라우트는 기존 JWT guard를 사용한다. 쓰기는 소유자 행을 먼저 잠그고 트랜잭션 안에서 연결 양쪽의 소유자를 검증한다. 연결이 실제 바뀔 때만 revision을 증가시키고 반복 연결·해제는 증가시키지 않는다. 앱의 저장글 삭제 경로에서도 연결된 주제 revision을 증가시킨 후 FK cascade로 연결을 제거한다. 타인 항목과 없는 항목 모두 404로 처리한다.

완료 기준: 주제 생성·수정·삭제·복수 주제 연결·연결 해제·재접속 후 복원, 중복 클릭, 페이지네이션, 계정 전환 시 이전 데이터 제거, 타인 글 연결 거부를 자동 테스트한다. 이 단계에는 AI 호출이 없다.

구현 파일은 Backend `src/knowledge/`, Prisma 모델·migration, 기존 article 삭제 경로와 Frontend `knowledgeApi.ts`, `useKnowledgeLibrary.ts`, `KnowledgeScreen.tsx`다. `App.tsx`에서 보관함과 상세 메뉴의 진입·복귀만 연결한다. 계정 토큰으로 화면 상태를 격리하고 늦은 목록 응답은 조회 범위가 달라지면 폐기한다. 숨겨진 상세 화면은 읽음 처리와 Android 뒤로가기 이벤트를 소비하지 않는다.

실제 DB·HTTP 검증은 `READNEST_LOCAL_KNOWLEDGE_QA=1 node scripts/verify-knowledge-topics.cjs`로 재실행한다. 스크립트는 명시적 플래그와 로컬 MySQL `localhost/127.0.0.1:3307/readnest`만 허용한다. 실행마다 별도의 합성 사용자·자료를 생성하고 자신이 만든 사용자 ID만 정리하며, Redis worker나 모델을 실행하지 않는다. guard의 신원은 합성이므로 실제 JWT 서명·로그인 검증과 구분한다.

### 개별 글끼리 연결

주제 연결이 안정화된 뒤 ‘관련 글 연결’을 추가한다. `ArticleConnection`은 userId, 정렬된 두 articleId, 사용자 메모를 저장하고 두 ID 조합에 unique를 둔다. A→B와 B→A는 같은 연결이며 자기 자신 연결은 거부한다.

`PUT/DELETE /api/articles/:id/connections/:otherId`로 연결·해제하고 `GET /api/articles/:id/connections`로 양방향 목록을 조회한다. 양쪽 소유자를 확인하고 원본 글 삭제 시 연결은 제거한다. 두 글이 같은 주제인지와 사용자가 직접 연결했는지는 구분해 이유를 표시한다. 선택 미리보기만으로 읽음 처리를 하지 않으며 실제 상세 진입 시 기존 읽음 정책을 적용한다.

## 2단계 출처가 있는 Wiki 초안

### 사용자 경험

주제 화면에서 ‘Wiki 만들기’를 누르면 사용할 글을 선택하고 생성 범위를 확인한다. 원문이 없는 글은 선택할 수 없고 재수집 경로를 안내한다. 부분 수집 글은 경고를 표시하며 사용자가 알고 선택할 수 있다. UNKNOWN은 완전 수집으로 바꾸지 않는다.

생성 중에도 기존 Wiki를 읽고 사용자 메모를 편집할 수 있다. 새 결과는 **AI 초안**으로 분리해 보여주고 ‘검토 후 적용’ 전에는 기존 문서를 교체하지 않는다. 실패하면 이전 Wiki와 편집 내용은 그대로 남는다. 처음 만들 때는 실패·재시도 상태를 보이며 빈 문서를 완성본으로 표시하지 않는다.

AI 본문은 사실 목록이 아니라 주제별 설명으로 구성할 수 있지만, 저자의 상반된 주장·조건·시점 차이를 지우지 않는다. 사용자가 고르지 않은 글이나 외부 정보를 섞지 않는다.

### 데이터 설계

| 모델 | 책임 |
| --- | --- |
| KnowledgeSourceSnapshot | 소유자, 원본 글 참조, 생성 당시 제목·URL·rawText·수집 상태·본문 hash·resultGeneration·capturedAt; 삭제 시 민감 본문 제거 |
| WikiDocument | 소유자·주제·제목·revision·현재 승인된 revision 참조·별도 사용자 메모 |
| WikiRevision | 문서 버전·작성 유형 AI_DRAFT/USER_EDITED·구조화 본문·사용한 snapshot 참조·모델/프롬프트 버전·생성 시각 |
| KnowledgeTask | 소유자·종류 WIKI_DRAFT/QUESTION·입력 fingerprint·idempotency key·상태·lease·attempt·결과 checkpoint·오류 코드 |

테이블 이름은 구현 전 migration 리뷰에서 최종 확정한다. 기본 요약 테이블은 그대로 둔다. snapshot은 동일 소유자·글·본문 hash·수집 메타데이터가 같을 때 재사용할 수 있지만 사용자 간 공유 캐시는 두지 않는다.

본문 hash는 실제 원문 내용의 변경 여부, `resultGeneration`은 생성 이력을 나타낸다. 같은 원문을 재요약했다고 Wiki 내용이 반드시 달라졌다고 주장하지 않는다. 제목·URL·완전성 변경도 별도 비교한다. 모델이 원문을 읽은 당시 버전은 유지하고 최신 글과 달라지면 ‘출처 변경됨’을 표시한다.

### 인용 계약

모델에는 서버가 부여한 `S1`, `S2` 같은 출처 키와 원문을 자료로 전달한다. 원문 속 실행 지시는 따르지 않도록 시스템 지시와 자료를 분리하고, 도구 실행·외부 검색 권한은 주지 않는다.

초안은 `{title, sections: [{heading, claims: [{text, sourceKeys: []}]}]}` 형태의 내부 계약을 사용한다. 출처 키는 요청에 포함된 스냅샷에만 연결할 수 있다. 모델이 반환한 URL을 저장하거나 바로 열지 않는다. 실제 원문 URL과 앱 내부 경로는 서버의 소유자 검증된 글에서 결정한다.

제목·구조용 문구를 제외한 근거 주장은 출처 참조를 요구한다. 직접 인용을 제공할 경우 해당 구절이 스냅샷에 존재하는지도 검증한다. **키가 유효하거나 인용문이 존재해도 주장 전체의 의미적 타당성이 증명되는 것은 아니다.** 서로 다른 의견의 혼합, 숫자·조건 왜곡, 근거 없는 결론은 별도 평가 대상으로 남긴다.

클라이언트는 주장 옆에 ‘출처 1’ 같은 native 버튼을 제공한다. 출처를 누르면 제목·수집 시점·완전성·해당 원문을 확인할 수 있다. 링크를 누를 때마다 현재 권한과 삭제 상태를 다시 확인한다. WebView나 raw HTML을 도입하지 않는다.

사용자가 AI 문구를 바꾸면 USER_EDITED로 기록하고 기존 출처를 유지할지 검토하도록 한다. 출처가 연결돼 있다는 이유만으로 편집 후 문장이 검증됐다고 표시하지 않는다. 자유 메모는 근거 검증된 AI 주장과 별도 영역에 둔다.

| PATCH /api/knowledge/wiki/:id | expectedRevision과 사용자 편집 내용 |
| POST /api/knowledge/wiki/:id/apply-draft | draftId와 expectedRevision; 검토한 초안 적용 |

같은 idempotency key와 같은 입력은 같은 task를 반환한다. 동일 key로 다른 입력을 보내면 409다. 캐시 fingerprint에는 선택 원문 버전, 사용자 지시, 모델, 프롬프트 버전, 기능 종류를 포함한다. 모델만 바뀌었는데 오래된 생성물을 새 모델 결과로 표시하지 않는다.

DB에 task를 먼저 저장한 뒤 queue에 dispatch한다. 네트워크 호출은 DB 트랜잭션 밖에서 수행한다. worker lease·heartbeat·제한된 재시도·checkpoint를 사용하고, 저장 시 lease·원문 존재·소유자·문서 revision을 다시 확인한다. 실패한 작업이 승인된 Wiki를 덮어쓰지 않게 한다.

생성 중 사용자가 문서를 편집하면 초안은 별도로 남기되 자동 적용하지 않는다. 적용 시 revision 불일치는 409이며 사용자가 두 버전을 확인하고 다시 적용하도록 한다. 출처가 삭제된 초안은 적용을 막는다. 단순 내용 변경은 변경 경고와 함께 재생성하거나 당시 출처 기준임을 확인하는 선택을 제공한다.

## 3단계 선택한 자료에 질문

첫 버전은 선택한 글 또는 주제 안에서 사용자가 확인한 글 묶음으로 범위를 한정한다. 주제가 크면 전체를 읽었다고 표시하지 말고 선택 범위·제외 이유를 먼저 보여준다. 관련 원문을 검색해 자동으로 선택하는 기능은 검색 품질 검증 후 확장한다.

`POST /api/knowledge/questions`에 `articleIds`, `question`, idempotency key를 전달하고 202 + taskId를 반환한다. 결과는 소유자 전용 `GET /api/knowledge/questions/:id`로 조회한다. 질문도 생성 당시 원문 snapshot을 사용한다. 이전 답변만 이어받아 추론하는 대화형 기능은 초기 범위에서 제외한다.

답변 상태는 ANSWERED / INSUFFICIENT_EVIDENCE로 구분한다. 기술적 실패는 FAILED이며 근거 부족과 다르다. ‘자료에서 확인할 수 없음’을 정상 결과로 지원한다. 의견이 갈리면 출처별 차이를 제시하고 서비스가 임의로 승자를 정하지 않는다.

답변은 주장별 출처를 가진 구조화 블록으로 저장하며 Wiki와 같은 인용 UI를 사용한다. 질문 기록은 삭제 가능해야 한다. 질문을 Wiki에 반영할 때도 별도 초안으로 제안하고 사용자 확인 없이 본문에 추가하지 않는다.

## 출처 변경과 삭제

| 사건 | 처리 제안 |
| --- | --- |
| 주제에서 글 연결 해제 | 저장글·기존 사용자 Wiki는 유지. 이후 새 생성 대상에서 제외 |
| 저장글 원문 변경 | 기존 snapshot 기준 결과 유지, 변경 배지 표시, 명시적 재생성 제안 |
| 저장글 삭제 | snapshot 원문·제목·URL·인용 발췌문 제거, SOURCE_DELETED 상태만 유지 |
| 삭제된 출처를 사용하는 미승인 AI 초안·질문 답변 | 본문과 checkpoint 제거, 재생성 안내. 진행 중 작업은 취소하고 늦은 저장도 차단 |
| 삭제된 출처를 참조하는 사용자 저장 Wiki·메모 | 자동 삭제하지 않음. 출처 삭제 배지와 끊어진 인용 안내. 사용자가 본문을 수정·삭제 가능 |
| Wiki 삭제 | Wiki와 버전·관련 생성 결과 제거, 원본 저장글 유지 |
| 주제 삭제 | 연결 제거. 연결된 Wiki는 주제 참조를 해제해 ‘미분류 Wiki’로 유지하고 저장글도 보존. Wiki 삭제는 별도 액션 |
| 계정 삭제 | 주제·연결·Wiki·버전·snapshot·작업·질문까지 계정 범위 삭제 |

원문 삭제가 사용자가 직접 저장한 Wiki의 모든 파생 문장 삭제까지 의미하지는 않는다. 삭제 화면에 이 차이를 명시한다. 유출 방지를 위해 삭제 이후에는 캐시·polling 결과·다운로드 경로에서도 스냅샷이 다시 노출되지 않아야 한다. 서버 밖으로 이미 복사한 Obsidian 노트는 서비스가 회수할 수 없다.

삭제와 worker 저장이 동시에 일어나면 snapshot 행 잠금 또는 이에 준하는 조건부 저장으로 순서를 보장한다. 취소 플래그만 확인한 뒤 무조건 저장하지 않는다. 이미 외부 모델로 전달된 요청을 취소해 처리나 과금이 완전히 사라진다고 약속하지 않는다.

## 화면 상태와 접근성

- 주제 목록·상세는 loading, empty, ready, error를 분리한다. 필터 변경·계정 전환 후 늦은 응답을 폐기한다.
- 자료 선택 화면은 실제 선택 개수, 준비되지 않은 원문, 부분 수집 경고와 생성 요청 범위를 표시한다.
- Wiki 편집 화면은 읽기·편집·AI 초안을 구분한다. 저장하지 않은 변경이 있으면 이동·뒤로가기 전에 보존 또는 폐기를 선택한다.
- ‘사용자가 확인한 문서’는 편집·적용 상태이지 사실 검증 인증이 아니다. 저장 실패나 409 충돌 시 로컬 편집 내용을 유지하고 복사·비교·다시 불러오기 방법을 제공한다.
- 출처 열기는 Wiki 복귀 위치를 보존한다. Android 뒤로가기와 modal 닫기, 웹 키보드 포커스를 검증한다.
- 생성 중 다시 요청을 막고 화면 재진입 시 taskId로 상태를 복원한다. 모바일에서 벗어나도 작업이 중단됐다고 오해시키지 않는다.
- 본문은 기존 파란색·산세리프·문서형 읽기 스타일을 유지한다. 각 문단을 중첩 카드로 만들지 않는다.
- 제목·본문·출처·액션 순서가 스크린리더에서 자연스럽게 이어지고, 44×44px 이상 액션과 320px/200% 글자 크기를 검증한다. 성공·실패·출처 변경은 색만으로 전달하지 않는다.

## 비용과 지연 제어

초기 제안은 요청당 최대 10개 원문, 총 입력 본문 100,000자 이내, 사용자당 AI 작업 1개 동시 실행이다. 이는 원문의 항목 수나 요약 길이를 강제하는 규칙이 아니라 호출량 제한이다. 코드포인트 기준을 명시하고 실제 토큰 예산·동시 사용자 수를 측정해 조정한다. 한도를 넘으면 선택을 줄이도록 안내하고 뒤쪽 자료를 몰래 자르지 않는다.

일일 호출 한도·글로벌 worker 동시성은 운영 비용 예산을 정한 뒤 설정한다. 운영에서 제한값이 빠지면 무제한 실행하지 않는다. 조회나 주제 연결만으로 AI를 호출하지 않는다. 정해진 근거·출력 검증 실패에 무한 재생성하지 않으며, transient 오류에만 제한된 재시도를 적용한다.

Wiki와 기본 요약은 queue를 분리하되 같은 모델 계정의 rate limit과 비용 한도를 공유한다는 점을 고려한다. Wiki로 인해 기본 요약 지연이 증가하는지 측정한다. 계측은 queue 대기, 자료 준비, 첫 응답, 생성 완료, 저장, 화면 표시를 구분한다. 토큰·모델·프롬프트 버전·시도 수는 기록하되 원문 전문·키·토큰을 진단 로그에 남기지 않는다.

## 검증과 구현 순서

| 순서 | 담당 범위 | 완료 조건 |
| --- | --- | --- |
| 1 | Backend 주제 CRUD·연결·권한·migration | 타인 접근·중복 연결·삭제 정책·cursor 회귀 검증 |
| 2 | Frontend 주제 목록·상세·선택 UI | 실제 저장·재진입·연결 해제·오류 복구·기존 상세 회귀 검증 |
| 3 | Backend snapshot·Wiki task·구조화 인용 | lease 복구·중복 요청·출처 위조·삭제 경쟁·원문 변경 검증 |
| 4 | Frontend Wiki 읽기·출처·편집·초안 적용 | 미저장 변경 보호·409 복구·출처 복귀·부분 수집 표시 |
| 5 | Backend와 Frontend 선택 자료 질문 | 근거 부족·상반된 주장·질문 삭제·사용자 격리 검증 |
| 6 | 실호출 품질·성능·기기 검증 | 아래 평가 세트와 성능 보고, 남은 한계 공개 |

평가 세트에는 같은 주제의 보완 자료, 서로 반대되는 주장, 시점이 다른 수치, 원문 없는 글, 부분 수집, 질문과 무관한 자료, 악성 실행 지시가 포함된 본문, 생성 중 삭제·원문 변경을 넣는다. mock 테스트는 API 계약과 예외 처리를 검증하고 실제 모델의 의미적 정확성 증명으로 사용하지 않는다. 실호출 비용·횟수를 정하고 결과의 주장별 근거를 사람이 대조한다.

각 단계는 build·관련 자동 테스트·typecheck·diff 리뷰 후 별도로 커밋한다. migration은 로컬/검증 환경에서 먼저 적용하고 운영 적용은 별도 배포 범위로 다룬다. 성공 기준 없는 일괄 자동 분류나 자동 Wiki 재작성은 추가하지 않는다.

## 구현 파일 배치 제안

- Backend: `readnest-api/src/knowledge/`에 controller, service, DTO, job/processor, source/citation 검증과 테스트를 둔다. `app.module.ts`, Prisma schema와 새 migration, 저장글 삭제 경로의 참조 정리만 연결한다.
- Frontend: `readnest-mobile/src/api/knowledgeApi.ts`, `hooks/useKnowledgeLibrary.ts`, 주제·Wiki 화면, 출처/편집 컴포넌트를 분리한다. 기존 `App.tsx`에는 진입·복귀 라우팅만 연결한다.
- 기존 summary service의 사용자 요약 프롬프트는 Wiki용으로 바꾸지 않는다. 모델 설정과 제한된 전송 코드의 재사용 여부는 실제 중복이 생길 때 판단한다.
- 테스트 fixture는 `fixtures/`에 인용 유효/무효·삭제·부분 출처 계약을 공유한다. 새 문법 때문에 기존 요약 contract fixture를 완화하지 않는다.

## 후속 결정이 필요한 항목

수동 주제·저장글 연결 다음에는 개별 글 직접 연결 또는 출처 스냅샷 기반 Wiki 초안을 진행할 수 있다. 전체 보관함 검색과 Wiki 편집의 우선순위는 사용자 피드백으로 조정한다. 운영 호출 예산, 자료 보관 범위, 자동 추천의 수용 기준은 출시 전에 확정한다. 확정 전에는 후속 단계의 제안값을 운영 설정으로 간주하지 않는다.
