# 요약 지연 현황과 우선 개선 계획

- 기록일: 2026-09-30
- 측정 기준 코드: `80c760d` (`main`)
- 우선순위: **P1 — 다음 성능·UX 작업에서 우선 조사·해결**
- 상태: 실호출 기준선 1회 확보. 반복 측정과 개선 구현은 미착수.
- 승인 범위: 문서화만 수행. 프롬프트·모델·UI·서버·DB 변경과 추가 유료 호출 없음.

## 1. 실제 측정과 한계

사용자가 요약 대기 시간을 길게 느끼고 있다. 실제 처리 시간과 읽기를 시작하기까지의 체감 대기 시간을 구분해 개선한다.

대상: [jsonjeong의 Threads 게시물](https://www.threads.com/@jsonjeong/post/Dd2Z8l5ANlC)

로컬 `readnest-api`의 `.env` 설정으로 현재 소스의 `ContentExtractorService.extract()`와 `AiSummaryService.summarize()`를 순차 실행했다. 실제 모델은 `gpt-5.6-luna`, 밀도는 `STANDARD`다. mock 응답이 아니며 키 값은 출력하지 않았다.

| 지표 | 결과 |
| --- | --- |
| 원문 수집 | 1,551ms (1.55초) |
| AI 요청부터 최종 요약 반환 | 8,257ms (8.26초) |
| 수집 시작부터 요약 반환 | 9,808ms (9.81초) |
| AI 구간 비중 | 약 84.2% |
| 수집 결과 | SUCCESS, structured source 5개 부분 |
| 본문 길이 | 1,071 (`text.length`, JS UTF-16 코드 단위) |
| 원문 완전성 | UNKNOWN — 전체 수집 보장 아님 |
| 생성 결과 | 성공: 제목·도입·4개 핵심 항목·한 줄 요약 |

**한계:** 단일 링크·단일 호출이며 평균이나 p95가 아니다. 앱 요청, 큐 대기, DB 저장, 완료 알림, 화면 렌더링 시간은 제외했다. AI 구간은 네트워크·제공자 대기와 처리·출력 생성·로컬 후처리를 포함하며 각각 분리하지 않았다. 첫 토큰 시간, 토큰량, 출력 길이, 서버 부하는 미측정이다. 별도 영구 원시 로그 파일은 없으며 수치는 해당 실행 도구 출력에서 옮겼다.

## 2. 추정 원인·해결 후보·기대 효과

아래는 확정 원인이 아닌 가설이며 기대 효과도 검증 전이다.

| 추정 원인 | 확인 방법 | 해결 후보 | 기대 효과와 주의점 |
| --- | --- | --- | --- |
| 모델 대기·처리·출력 생성 | 첫 응답/완료 시간, 토큰량, 재시도 기록 | 중복 설명·기술 나열 점검, 필요 시 모델·설정 비교 | 생성 시간·비용 감소 가능. 독립 항목·조건·예외 보존 |
| 완성 전까지 본문을 읽을 수 없음 | 첫 읽을 수 있는 문단 표시 시점 측정 | 스트리밍 또는 문단 단위 점진 표시 | 읽기 시작 단축. 전체 완료 시간 단축은 보장하지 않음 |
| 일부 링크의 브라우저 수집·네트워크 대기 | HTTP/브라우저 경로별 시간·수집 범위 비교 | 불필요한 대기 제거, 저장 원문 재사용 정책 검토 | 느린 사례 감소. 일부 본문만 채택해 속도를 얻지 않음 |
| 작업 등록부터 실행까지 큐 대기 | 등록·enqueue·claim 시각, 동시 작업량 기록 | 즉시 dispatch 확인, worker 설정 검토 | 시작 대기 감소. 동시성 증가는 rate limit·비용 위험 |
| 완료 후 화면 갱신 지연 | DB 완료부터 화면 표시까지 추적 | 완료 이벤트 또는 적응형 상태 조회 | 끝난 요약을 빨리 표시. 과도한 polling 방지 |
| 재수집·중복 요청·불필요한 재시도 | 요청 키·generation·attempt별 호출 수 확인 | 기존 중복 방지 검증, 오류별 재시도, 재수집/재요약 분리 검토 | 중복 과금·부하 감소. 명시적 재수집 의도 보존 |
| 밀도 변경 때 추가 생성 대기 | 캐시 hit/miss별 표시 시간 측정 | 이미 생성한 모드 재사용, 생성 중 기존 본문 유지 검증 | 반복 전환 즉시 표시. 세 모드 무조건 선생성하지 않음 |

코드의 5초 dispatch 점검 주기와 2.5초 클라이언트 조회 주기는 실제 지연 확정치가 아니다. 즉시 dispatch 경로도 있으므로 9.81초에 단순 가산하지 않는다. 원문 재사용·모드 캐시의 기존 구현과 추가 개선 후보도 구분한다.

## 3. 권장 해결 순서

1. **앱 전체 경로 계측:** 요청 → 큐 대기 → 수집 → AI 첫 응답 → 생성 완료 → 저장 → 화면 표시를 동일 작업 식별자로 연결한다. 키·인증 토큰·원문 전문은 성능 로그에 남기지 않는다.
2. **반복 기준선 확보:** 짧은 글·긴 글·연속 게시물, 최초 생성·밀도 캐시 hit/miss를 구분한다. 초기 유형별 3회 수준으로 편차를 탐색하고 표본이 부족한 상태에서 p95를 주장하지 않는다. 추가 호출 비용·횟수는 실행 전에 정한다.
3. **품질과 무관한 지연부터 제거:** dispatch, 중복 호출, 불필요한 재수집, 화면 갱신을 먼저 점검한다. 모델과 프롬프트를 동시에 바꾸지 않는다.
4. **대기 상태 안내:** 실제 단계에 맞는 ‘원문 가져오는 중 / 요약 작성 중 / 저장 중’을 표시한다. 근거 없는 진행률·남은 시간은 제시하지 않는다.
5. **점진 표시 검토:** 미완성 Markdown, 화면 흔들림, 연결 종료·재접속, 백그라운드 복귀, 스크린리더 알림을 설계한다. 작성 중 결과와 검증·저장된 완성본을 구분하고 실패 시 기존 완성본을 유지한다.
6. **잔여 병목 최적화:** 동일 원문으로 출력 중복·모델·설정의 속도와 품질을 비교한다. 고정 항목 수나 강제 분량 제한으로 의미를 훼손하지 않는다.

초 단위 성능 목표는 반복 측정 후 정한다. 현재 단축 시간을 약속하지 않는다. 기대 이점은 빠른 읽기 시작, 대기 불확실성 및 불필요한 재시도 감소, 중복 비용 절감이며 실제 효과는 후속 검증 대상이다.
