# 통합 Markdown 요약 설계

> 현행 요약 계약. 2026-09-29 제품·UX 신뢰성 구현에 맞춰 갱신했습니다. [개선 계획](PRODUCT_UX_IMPROVEMENT_PLAN.md)과 [구현·검증·적용 기록](PRODUCT_UX_IMPLEMENTATION_REPORT.md)을 함께 확인합니다. 프롬프트와 단일 Markdown 본문 계약은 유지했습니다. 코드 반영과 운영 배포는 별개입니다.

## 현재 결정

AI 호출에는 기존 요약 편집 원칙, Markdown 출력 형식, 길이 기준을 제공한 뒤 마지막에 `다음 글을 요약해줘.`와 원문을 넣는다. 유효한 모델 응답은 그대로 `summaryMeta.summaryMarkdown`에 저장한다. 수집·작업 소유권·저장 신뢰성은 별도로 강화하며, 요약 내용을 다시 작성하거나 항목 수를 강제하지 않는다.

## 처리 흐름

1. 지원하는 Threads URL을 검증하고 원문을 안전한 연결 예산 내에서 수집한다. 새 원문은 이전 수집 결과와 합치지 않는다. 비어 있거나 실패한 원문으로 AI를 호출하지 않는다.
2. 요약 편집 프롬프트와 `다음 글을 요약해줘.\n\n{원문}`으로 Luna를 호출한다.
3. 응답 텍스트를 trim한 뒤 안전한 Markdown인지 검증한다.
4. 검증된 응답을 상세 화면의 단일 요약 본문으로 저장한다.
5. 빈 응답, 위험한 HTML·링크·코드·표 또는 길이 초과 응답은 실패 처리한다. 형식 오류는 자동 재호출하지 않으며 사용자가 명시적으로 다시 생성할 수 있다. 일시 장애는 작업 단위 제한 재시도와 cooldown을 적용한다.
6. 저장글 제목은 Markdown 첫 H1을 우선 사용한다. H1이 없으면 추출 제목, URL 기반 제목 순으로 사용하며, 저장 직전에 Unicode 문자 기준 191자로 제한한다. 제목 추출 품질 문제로 요약 저장 전체가 실패하지 않게 한다.

## 데이터 계약

`summaryMeta.summaryMarkdown`이 상세 요약의 유일한 본문이다. 기존 `summary`, `oneLineSummary`, `keyPoints`, `tags` 필드는 API와 목록 호환을 위해 유지하지만, 상세 화면의 대체 요약으로 사용하지 않는다.

AI 응답에서 별도 구조화 JSON이나 내부 요약 문서를 요구하지 않는다. Backend는 응답을 임의로 재작성하거나 번호·항목·문단을 생성하지 않는다.

생성 요청 `generation`과 마지막 성공 본문 `resultGeneration`/`generatedAt`을 구분한다. DB 작업 레코드와 lease가 현재 작업임을 보장할 때만 본문을 교체한다. 재요약 중·실패 시 마지막 정상 본문 하나를 유지하며, 이는 다른 요약 형식으로 전환하는 fallback이 아니다. `summaryPreview`는 이 본문의 첫 실제 문단을 추출한 목록용 표현이지 두 번째 AI 요약이 아니다.

## 읽기 밀도 규칙

- 요약은 원문을 대체하지 않지만, 사용자가 짧은 시간 안에 핵심 주장과 다시 읽을 가치를 떠올리게 하는 회상용 문서다.
- 원문의 항목 수를 기계적으로 유지하거나 줄이지 않는다. 반복 의미만 합치고, 독립적인 주장·조건·비교·수치·주의사항은 보존한다.
- 도입부는 핵심 주장과 배경을 합친 최대 두 문장의 한 문단으로 작성한다.
- 번호형 핵심 항목은 각각 기본 1~2문장으로 압축한다. 중요한 수치·비교·조건·인과관계를 보존해야 할 때만 3문장을 허용하고, 먼저 중복·부연 표현을 줄인다.
- 전문 용어는 이해에 꼭 필요할 때만 사용하고, 낯선 용어는 처음 한 번 짧게 풀어 쓰거나 생략한다.
- 마지막 `### 한 줄 요약`은 전체 메시지를 한 문장으로 굵게 강조하며, 그 뒤에 결론을 반복하지 않는다.
- 문장 수를 하드 검증하거나, 문장 수만을 이유로 모델에 재요약을 강제하지 않는다. 의미 보존을 우선하는 소프트 가이드로 적용한다.
- 원문에 없는 사용자의 의도, 평가, 조언은 추가하지 않는다.

## 길이와 형식

- 원문 대비 비율 제한 없음
- 항목별 글자 수 제한 없음
- 항목 개수 강제 없음
- 글의 길이와 구조에 따라 모델이 자연스럽게 결정
- 저장 안전성을 위한 전체 Markdown 상한은 유지
- 저장글 제목은 MySQL `VARCHAR(191)` 제한 안에 항상 들어가도록 축약
- raw HTML, iframe, 이미지, 표, 코드 펜스, 위험 링크는 거부

## Frontend

- 유효한 `summaryMarkdown` 전체를 문서 흐름으로 표시한다.
- 기존 핵심 한 줄 요약·핵심 포인트·자세한 요약을 별도 카드로 중복 표시하지 않는다.
- Markdown이 없으면 `요약 생성` 상태만 표시한다.
- 최초 생성의 `SUMMARIZING`에서는 가짜 완성 본문을 표시하지 않는다. 재요약 중에는 이전 정상 본문임을 안내하고 기존 문서를 유지한다.
- `SUMMARY_FAILED`에서는 안전한 오류와 재시도/대기시간을 표시한다. 이전 정상 본문이 있으면 함께 보존한다.
- 복사·공유는 저장된 Markdown 전체와 원문 URL을 사용한다. 접힘 여부와 무관하며 복사 성공은 2초 표시·스크린리더 알림으로 전달한다.
- h1, h2, h3, paragraph, bold, ordered list, unordered list, blockquote, 줄바꿈을 지원한다.
- 제목은 한 번, 도입·원문/복사 액션·나머지 본문 순서다. 긴 글은 중간을 건너뛰지 않는 연속 의미 단위로만 접는다.
- 같은 글 진입에서 유효한 본문 첫 노출에만 자동 읽음을 한 번 적용한다. 사용자의 수동 안 읽음·다시 보기 선택이 우선한다.

- Luna 응답 Markdown 저장 검증

## 2026-09-29 구현 및 후속 검증

- 첫 H1 대신 실제 문단을 preview로 사용한다. 과거 저장 데이터에 preview가 없으면 서버가 해당 목록 페이지의 기존 Markdown을 한 번에 조회해 계산한다. 상세에서도 같은 규칙으로 추출하며 과거 데이터를 임의로 재요약하지 않는다.
- Frontend/Backend는 공통 허용 fixture를 검사한다. 문장 속 `A | B | C`는 허용하고 표/HTML/이미지/Markdown 링크/코드 펜스는 거부한다.
- 긴 문서의 연속 prefix, 번호·soft/hard break, 상태·복사·읽음 회귀 테스트를 추가했다.
- extractor는 공개 JSON에서 요청한 post ID/작성자와 같은 media ID의 self-thread를 확인해 원문을 결합한다. 전체 공개/비공개 parts까지 입증하지는 않으므로 `UNKNOWN` 또는 확인된 제한에 따른 `PARTIAL`만 반환한다. 글자 수로 본문 여부를 판단하지 않는다. [수집 회귀 수정 기록](THREADS_EXTRACTION_REGRESSION_20260929.md)을 따른다.
- 실제 모델 품질, 완전한 연속 글 수집, native 200%/스크린리더 검증은 자동 테스트와 별개다. 최신 실측과 남은 위험은 [구현 기록](PRODUCT_UX_IMPLEMENTATION_REPORT.md)에 분리한다.
