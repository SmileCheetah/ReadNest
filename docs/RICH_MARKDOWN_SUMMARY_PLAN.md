# 통합 Markdown 요약 설계

## 현재 결정

원문 추출과 저장 흐름은 유지한다. AI 호출에는 요약 편집 원칙, Markdown 출력 형식, 길이 기준을 제공한 뒤 마지막에 `다음 글을 요약해줘.`와 원문을 넣는다. 모델의 응답은 그대로 `summaryMeta.summaryMarkdown`에 저장한다.

## 처리 흐름

1. 저장된 원문을 기존 extractor로 가져온다.
2. 요약 편집 프롬프트와 `다음 글을 요약해줘.\n\n{원문}`으로 Luna를 호출한다.
3. 응답 텍스트를 trim한 뒤 안전한 Markdown인지 검증한다.
4. 검증된 응답을 상세 화면의 단일 요약 본문으로 저장한다.
5. 빈 응답, 위험한 HTML·링크·코드·표 또는 길이 초과 응답은 실패 처리하고 재시도한다.
6. 저장글 제목은 Markdown 첫 H1을 우선 사용한다. H1이 없으면 추출 제목, URL 기반 제목 순으로 사용하며, 저장 직전에 Unicode 문자 기준 191자로 제한한다. 제목 추출 품질 문제로 요약 저장 전체가 실패하지 않게 한다.

## 데이터 계약

`summaryMeta.summaryMarkdown`이 상세 요약의 유일한 본문이다. 기존 `summary`, `oneLineSummary`, `keyPoints`, `tags` 필드는 API와 목록 호환을 위해 유지하지만, 상세 화면의 대체 요약으로 사용하지 않는다.

AI 응답에서 별도 구조화 JSON이나 내부 요약 문서를 요구하지 않는다. Backend는 응답을 임의로 재작성하거나 번호·항목·문단을 생성하지 않는다.

## 읽기 밀도 규칙

- 요약은 원문을 대체하지 않지만, 사용자가 짧은 시간 안에 핵심 주장과 다시 읽을 가치를 떠올리게 하는 회상용 문서다.
- 원문의 항목 수를 기계적으로 유지하거나 줄이지 않는다. 반복 의미만 합치고, 독립적인 주장·조건·비교·수치·주의사항은 보존한다.
- 도입부는 핵심 주장과 배경을 합친 최대 두 문장의 한 문단으로 작성한다.
- 번호형 핵심 항목은 각각 기본 1~2문장으로 압축한다. 중요한 수치·비교·조건·인과관계를 보존해야 할 때만 3문장을 허용하고, 먼저 중복·부연 표현을 줄인다.
- 전문 용어는 이해에 꼭 필요할 때만 사용하고, 낯선 용어는 처음 한 번 짧게 풀어 쓰거나 생략한다.
- 마지막 `### 한 줄 요약`은 전체 메시지를 한 문장으로 굵게 강조하며, 그 뒤에 결론을 반복하지 않는다.
- 문장 수를 하드 검증하거나, 문장 수만을 이유로 모델에 재요약을 강제하지 않는다. 의미 보존을 우선하는 소프트 가이드로 적용한다.
- 원문에 없는 사용자의 의도, 평가, 조언은 추가하지 않는다.

## 길이와 형식

- 원문 대비 비율 제한 없음
- 항목별 글자 수 제한 없음
- 항목 개수 강제 없음
- 글의 길이와 구조에 따라 모델이 자연스럽게 결정
- 저장 안전성을 위한 전체 Markdown 상한은 유지
- 저장글 제목은 MySQL `VARCHAR(191)` 제한 안에 항상 들어가도록 축약
- raw HTML, iframe, 이미지, 표, 코드 펜스, 위험 링크는 거부

## Frontend

- 유효한 `summaryMarkdown` 전체를 문서 흐름으로 표시한다.
- 기존 핵심 한 줄 요약·핵심 포인트·자세한 요약을 별도 카드로 중복 표시하지 않는다.
- Markdown이 없으면 `요약 생성` 상태만 표시한다.
- `SUMMARIZING`에서는 완성된 본문을 표시하지 않는다.
- `SUMMARY_FAILED`에서는 오류와 재시도 버튼을 표시한다.
- 복사·공유는 저장된 Markdown 전체를 사용한다.
- h1, h2, h3, paragraph, bold, ordered list, unordered list, blockquote, 줄바꿈을 지원한다.

## 테스트

- 정확한 프롬프트 문자열 검증
- Luna 응답 Markdown 저장 검증
- 빈 응답·실패·위험 문법 처리
- 한글·영문·기술 용어 혼합 문장
- 번호·목록·인용문이 있는 응답을 임의로 변경하지 않는지 확인
- 320px 폭, 200% 글자 크기, 접근성 확인
