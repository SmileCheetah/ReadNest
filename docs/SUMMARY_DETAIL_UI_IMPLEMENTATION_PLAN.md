# 저장 콘텐츠 상세 화면 UI/UX 적용 계획

## 문서 상태

- 상태: 구현 전 확정안
- 대상: `readnest-mobile` 상세 화면과 관련 API 계약
- 원칙: 이 문서를 상세 화면 개편의 단일 소스로 사용한다.
- 범위: 화면 정보 구조, 요약 표현, 액션 우선순위, 상태·오류·접근성, 필요한 백엔드 후속 작업
- 비범위: 검색, 추천 로직, 새로운 요약 유형, 원문 수집 방식 전면 개편

## 1. 핵심 사용자 목적

사용자는 저장한 글의 상세 화면에 들어온 뒤 첫 화면에서 다음 질문에 빠르게 답할 수 있어야 한다.

1. 이 글은 무엇에 관한 글인가?
2. 핵심 주장은 무엇인가?
3. 중요한 내용은 무엇인가?
4. 더 읽을 가치가 있는가?
5. 원문을 볼 것인가, 나중에 볼 것인가?

핵심 성공 지표는 장식의 완성도가 아니라 `핵심 요약 인지 시간`, `원문 보기 도달률`, `상세 화면 이탈률`, `요약 재시도 성공률`이다.

## 2. 현재 구조와 주요 문제

현재 상세 화면은 `readnest-mobile/App.tsx`의 `ThreadDetail`에 구현되어 있다. 하나의 큰 파일 안에서 화면, 상태, 네트워크 동작과 스타일을 함께 관리한다.

### P0 — 핵심 요약이 첫 화면 아래로 밀림

현재 문제 → 제목, 분석 메타데이터, 태그와 여러 작업 버튼이 요약보다 먼저 나온다.

왜 문제인지 → 상세 화면의 핵심 목적은 저장글 관리가 아니라 내용 파악인데, 첫 화면의 시각적 우선순위가 반대로 되어 있다.

개선 방향 → 출처·제목 다음에 `oneLineSummary`와 `keyPoints`를 바로 노출한다.

구체적 변경안 → 메타데이터와 태그를 하단으로 내리고, 작업 버튼은 원문 보기와 요약 복사만 즉시 노출한다.

### P0 — 구조화 데이터가 UI에서 사용되지 않음

현재 문제 → API는 `summaryMeta.oneLineSummary`, `summaryMeta.coreSummary`, `keyPoints[]`를 제공하지만 상세 화면은 합쳐진 `thread.summary` 문자열만 렌더링한다.

왜 문제인지 → 번호, 문단, 항목 의미가 사라지고 동일 정보가 반복된다.

개선 방향 → 구조화 필드를 각각의 UI 컴포넌트에 직접 바인딩한다.

구체적 변경안 → `SummaryHero`, `KeyPointList`, `DetailedSummary`로 분리한다. 레거시 데이터에 `summaryMeta`가 없을 때만 `summary`를 대체 콘텐츠로 사용한다.

### P1 — 작업 버튼의 우선순위가 불명확함

현재 문제 → 읽음 변경, 나중에 보기, 원문, 원문 소스, 복사, 공유, 재시도, 삭제가 모두 비슷한 캡슐 버튼으로 표시된다.

왜 문제인지 → 사용자가 다음 행동을 고르기 어렵고 위험 작업인 삭제도 과도하게 눈에 띈다.

개선 방향 → Primary, contextual secondary, overflow action으로 구분한다.

구체적 변경안 → `원문 보기`만 파란색 채움 버튼으로 표시하고, 복사는 AI 요약 헤더에 둔다. 나머지는 더보기 메뉴로 이동한다.

### P1 — 상태와 신뢰도 표현이 사용자 언어가 아님

현재 문제 → `맥락`, `신뢰도 96%`, `threadStatus`가 설명 없이 노출된다.

왜 문제인지 → 모델이 생성한 confidence는 보정된 정확도 확률이 아니므로 정밀한 백분율처럼 표시하면 오해를 만든다.

개선 방향 → 맥락 상태와 사용자 행동만 보여주고 confidence 백분율은 숨긴다.

구체적 변경안 → 하단 `분석 정보` 접힘 영역에서 `완전한 원문`, `일부 원문`, `원문 부족`의 정성 상태와 주의 문구를 제공한다.

## 3. 확정 정보 구조

1. 앱바: 뒤로가기 / Unwind / 더보기
2. 출처와 저장일
3. 제목: 최대 3줄
4. AI 요약 헤더와 복사 액션
5. 핵심 한 줄 요약: 최대 2~3줄
6. 핵심 포인트: 기본 최대 3개
7. Primary CTA: 원문 보기
8. 조건부 상태·경고와 복구 액션
9. 자세한 요약: 기본 접힘
10. 대표 태그: 최대 3개
11. 분석 정보: 기본 접힘
12. 원문 소스: 더보기 메뉴에서 열기

제목은 26~30px, weight 700, line-height 1.25~1.35, letter-spacing 약 -0.02em을 기준으로 한다. 기존 산세리프 계열을 유지하고 글자 단위 줄바꿈을 피한다.

## 4. 디자인 쟁점 결정 기록

### 4.1 원문 보기 CTA 위치

문제 → 인라인 버튼은 긴 화면에서 사라지고, 하단 고정 버튼은 콘텐츠를 가릴 수 있다.

가능한 선택지 → 핵심 요약 직후 인라인 / 하단 고정 / 둘 다 노출.

선택한 방법 → 1차 구현은 핵심 요약 직후 인라인 버튼.

선택 이유 → 사용자가 내용을 파악한 직후 자연스럽게 원문으로 이동하며, safe-area와 키보드·스크롤 충돌이 없다.

트레이드오프 → 긴 상세 내용을 펼친 뒤에는 버튼이 보이지 않는다. 실제 사용 지표에서 필요성이 확인되면 sticky CTA를 후속 검토한다.

### 4.2 공유 위치

문제 → 공유를 직접 노출하면 액션이 다시 많아진다.

가능한 선택지 → 상단 아이콘 / 요약 헤더 / 더보기 메뉴.

선택한 방법 → 더보기 메뉴.

선택 이유 → 복사와 원문 보기가 더 자주 쓰이는 핵심 행동이다.

트레이드오프 → 공유까지 한 번 더 눌러야 한다.

### 4.3 분석 유형 위치

문제 → 제목 근처의 분석 유형 배지가 제목과 요약보다 먼저 읽힌다.

가능한 선택지 → 제목 인접 / AI 요약 헤더 / 하단 분석 정보.

선택한 방법 → 하단 분석 정보.

선택 이유 → 사용자는 모델의 분류보다 콘텐츠의 내용을 먼저 알아야 한다.

트레이드오프 → 유형을 활용해 빠르게 탐색하려는 사용성은 약해진다.

### 4.4 핵심 포인트 수

문제 → 항상 3개로 생성하면 원문의 중요한 5단계를 훼손할 수 있고, 가변 노출하면 첫 화면이 길어진다.

가능한 선택지 → 생성부터 정확히 3개 / 전체 가변 노출 / 전체 저장 후 3개만 우선 노출.

선택한 방법 → API에는 2~5개를 보존하고 첫 화면에는 최대 3개만 노출한다. 나머지는 자세한 요약에서 확인한다.

선택 이유 → 정보 보존과 빠른 스캔을 동시에 만족한다.

트레이드오프 → 어떤 3개를 대표로 선택할지 생성 순서의 품질에 의존한다.

### 4.5 자세한 요약의 기본 노출

문제 → 전체 노출은 스크롤을 늘리고, 완전 접힘은 중요한 맥락을 숨긴다.

가능한 선택지 → 전체 노출 / 일부 미리보기 / 완전 접힘.

선택한 방법 → 핵심 한 줄과 3개 포인트를 먼저 표시하고 `coreSummary`와 결론은 기본 접힘.

선택 이유 → 첫 화면의 목적을 지키면서 사용자가 필요할 때 맥락을 확장할 수 있다.

트레이드오프 → 상세 내용을 읽으려면 추가 탭이 필요하다.

### 4.6 신뢰도 표시

문제 → 현재 confidence는 모델이 생성한 자기평가 값이며 실제 정확도로 보정되지 않았다.

가능한 선택지 → 백분율 유지 / 높음·보통·낮음으로 변환 / 사용자 화면에서 숨김.

선택한 방법 → 백분율은 숨긴다. `contextStatus`, `caution`, 추출 성공 여부로 행동 가능한 상태를 표시한다.

선택 이유 → 설명할 수 없는 정밀도를 사용자에게 제공하지 않기 위함이다.

트레이드오프 → 내부 품질 신호가 사용자에게 직접 보이지 않는다. confidence는 운영 분석과 향후 보정 실험에는 유지한다.

## 5. 주요 사용자 흐름

### 정상 요약

상세 진입 → 제목 확인 → 한 줄 요약 확인 → 핵심 포인트 확인 → 원문 보기 또는 자세히 보기.

### 요약 복사

복사 선택 → `oneLineSummary + keyPoints + 원문 URL`을 문자열로 구성 → 클립보드 저장 → 약 2초간 `✓ 복사됨` → 원래 상태 복귀.

### 요약 실패

실패 상태 확인 → 사용자 친화적 오류 문구 → 재시도 선택 → 중복 탭 방지 → `SUMMARIZING` 표시 → 완료 시 새 데이터 반영.

### 삭제

더보기 → 삭제 → 확인 다이얼로그 → 서버 삭제 성공 → 상세 화면 종료와 목록 갱신.

실행 취소는 1차 UI 개편 범위에서 제공하지 않는다. 현재 API가 hard delete이므로 서버 복구 계약 없이 실행 취소 토스트를 표시해서는 안 된다.

## 6. API와 데이터 계약

### 6.1 1차 UI 개편

기존 `GET /articles/:id` 응답을 유지한다. 파괴적 API 변경은 없다.

프론트가 사용하는 우선순위:

| UI | 1순위 필드 | fallback |
| --- | --- | --- |
| 표시 제목 | `summaryMeta.title` 또는 `title` | `제목 없음` |
| 한 줄 요약 | `summaryMeta.oneLineSummary` | `summary` 미리보기 |
| 핵심 포인트 | `keyPoints[]` | 빈 상태 문구 |
| 상세 요약 | `summaryMeta.coreSummary` | `summary` |
| 대표 태그 | `tags[0..2]` | 숨김 |
| 맥락 상태 | `summaryMeta.contextStatus` | `processStatus` |
| 주의 문구 | `summaryMeta.caution` | 상태별 기본 문구 |

`keyPoints`는 API에서 2~5개를 유지하며 프론트가 처음 3개만 표시한다. 목록 원소가 빈 문자열이면 렌더링 전에 제거한다.

### 6.2 삭제 실행 취소 후속 설계

문제 → 현재 `DELETE /articles/:id`는 즉시 hard delete하고 연관 ThreadPart도 cascade 삭제한다.

가능한 선택지 → 클라이언트에서 삭제 요청을 지연 / 삭제 데이터를 별도 테이블에 보관 / `deletedAt` soft delete와 restore API.

선택한 방법 → 실행 취소가 제품 요구사항으로 확정될 때 `deletedAt` soft delete와 `POST /articles/:id/restore`를 도입한다.

선택 이유 → 앱 종료, 네트워크 재연결, 다중 기기에서도 복구 계약이 명확하고 서버가 최종 상태를 소유한다.

트레이드오프 → 모든 조회에 `deletedAt: null` 조건이 필요하고, 현재 `(userId, normalizedUrl)` unique 제약과 재저장 동작을 함께 설계해야 한다.

후속 계약:

- `DELETE /articles/:id`: 멱등하게 `deletedAt` 설정. 이미 삭제되었으면 동일 성공 응답.
- `POST /articles/:id/restore`: 소유자이며 보존 기간 내인 경우 복구. 이미 활성 상태면 동일 성공 응답.
- 삭제 응답: `{ id, deleted: true, undoExpiresAt }`
- 복구 응답: 전체 `ApiArticle`
- 기본 보존 시간: 10초가 아니라 운영 복구를 고려해 24시간 이상. UI는 5초 동안만 실행 취소를 노출한다.
- 생성 시 동일 URL의 soft-deleted 행이 있으면 새 행을 만들지 않고 해당 행을 재활성화할지 정책을 서비스 계층에서 명시한다.

## 7. 상태 변화와 동시성

### 요약 재시도

현재 위험 → 빠르게 여러 번 누르면 `summaryRetryCount` 확인과 증가 사이에 race condition이 발생할 수 있고 동일 article에 여러 BullMQ job이 등록될 수 있다. 현재 queue job에 고정 `jobId`도 없다.

권고 → 재시도 API는 `SUMMARY_FAILED` 또는 `CONTEXT_INSUFFICIENT` 상태에서만 허용하고, 조건부 update 또는 트랜잭션으로 상태와 카운트를 갱신한다. queue jobId를 `summary:{articleId}` 계열로 정해 중복 실행을 막고, 프론트도 요청 중 버튼을 비활성화한다.

트레이드오프 → 동일 article을 의도적으로 다시 요약하려면 완료 job 제거 정책과 버전 식별이 필요하다.

### 오래된 worker 결과

현재 위험 → 이전 job과 새 재시도 job이 동시에 실행되면 늦게 끝난 오래된 결과가 새 결과를 덮어쓸 수 있다.

권고 → `summaryGeneration` 또는 `summaryVersion`을 article에 저장하고 job payload에 포함한다. worker update 시 현재 version과 일치할 때만 결과를 반영한다.

### 삭제와 worker 경쟁

현재 hard delete에서는 worker의 마지막 update가 실패한다. soft delete 도입 시 worker가 삭제된 글에 결과를 쓰지 않도록 `deletedAt: null`과 generation 조건을 확인해야 한다.

## 8. Frontend 작업

### 구조 분리

- `ThreadDetail`을 별도 화면 파일로 이동한다.
- `SummaryHero`, `KeyPointList`, `DetailActionsMenu`, `SummaryStatusNotice`, `CollapsibleSection`, `TagList`로 분리한다.
- 상세 화면의 복사·메뉴·펼침 상태는 화면 내부 상태로 관리한다.
- 네트워크 변경은 상위 레벨 hook 또는 action 함수에 유지한다.

### 화면 변경

- 앱바의 삭제 아이콘을 더보기 아이콘으로 교체한다.
- 제목을 26~30px, weight 700, 최대 3줄로 제한한다.
- 메타데이터와 태그를 요약 아래로 이동한다.
- 한 줄 요약은 전체 bold를 피하고 2~3줄을 목표로 한다.
- `keyPoints`를 실제 목록으로 렌더링하며 처음 3개만 표시한다.
- 원문 보기 버튼을 요약 직후 유일한 Primary CTA로 둔다.
- 원문 URL이 없거나 열 수 없으면 버튼을 비활성화하고 이유를 표시한다.
- 원문 소스, 읽음 변경, 나중에 보기, 공유, 재요약, 삭제를 더보기 메뉴에 배치한다.
- `CONTEXT_INSUFFICIENT`와 `SUMMARY_FAILED`는 서로 다른 문구와 복구 행동을 사용한다.

### 복사 피드백

- `copyState: idle | copying | copied | failed` 상태를 둔다.
- 연속 탭 중에는 중복 실행하지 않는다.
- 성공 시 헤더 액션을 2초간 `✓ 복사됨`으로 변경한다.
- 실패 시 Alert 또는 접근 가능한 안내 영역으로 재시도 방법을 제공한다.

## 9. Backend 작업

### 1차 UI 개편 필수 작업

- API 스키마 변경은 필수 아님.
- `summaryMeta` JSON 파싱 결과가 예상 구조인지 응답 직전에 검증하거나 DTO 직렬화 계층을 추가한다.
- `keyPoints`와 `tags`가 배열이 아닐 때 안전한 빈 배열로 정규화한다.
- 요약 프롬프트가 `oneLineSummary`와 `keyPoints`를 중복 생성하지 않도록 책임을 명확히 한다.
- `keyPoints` 각 항목의 권장 길이와 최대 항목 수를 프롬프트 및 normalize 단계에서 제한한다.

### 안정성 후속 작업

- 재시도 요청의 원자성 및 멱등성 보강.
- summary generation/version을 이용한 오래된 결과 덮어쓰기 방지.
- 외부 AI API의 timeout, rate limit, 일시 오류, 영구 오류를 분류해 사용자 메시지와 재시도 정책을 분리.
- 상세 화면의 실행 취소가 확정되면 soft delete 및 restore API 구현.

## 10. 예외·오류·로딩 상태

| 상태 | 표시 | 사용자 행동 |
| --- | --- | --- |
| `SUMMARIZING` | 요약 skeleton과 `요약 중` | 화면 이탈 가능, 중복 재시도 금지 |
| `SUMMARY_DONE` | 구조화 요약 | 원문 보기·복사·상세 펼치기 |
| `SUMMARY_FAILED` | 실패 이유를 정리한 안내 | 재시도 |
| `CONTEXT_INSUFFICIENT` | 일부 원문 누락 경고 | 원문 확인·조건 충족 시 재시도 |
| `summaryMeta == null` | 레거시 `summary` 표시 | 정상 열람 가능 |
| `keyPoints == []` | 핵심 포인트 섹션 숨김 | 자세한 요약 제공 |
| 원문 URL 없음 | CTA 비활성화와 이유 | 없음 |
| URL 열기 실패 | 오류 안내 | 다시 시도 |
| 복사 실패 | 실패 안내 | 복사 재시도 |
| 네트워크 실패 | 기존 데이터 유지 | 다시 시도 |
| 삭제 실패 | 화면과 목록 유지 | 다시 시도 |

내부 예외 메시지와 외부 API 오류 원문을 사용자에게 그대로 노출하지 않는다.

## 11. 접근성 요구사항

- 모든 Pressable은 최소 44×44px 터치 영역을 확보한다.
- 아이콘 버튼에 `accessibilityRole`, `accessibilityLabel`, 필요 시 `accessibilityHint`를 제공한다.
- 핵심 포인트는 스크린리더가 항목 단위로 인식하도록 각 항목에 의미 있는 레이블을 제공한다.
- 접힘 영역에는 expanded 상태를 전달한다.
- 복사 완료는 시각 변화뿐 아니라 접근성 announcement로 알린다.
- 더보기 메뉴와 삭제 다이얼로그는 열릴 때 포커스를 이동하고 닫힌 뒤 트리거로 복귀한다.
- 200% 글자 확대, 긴 영문 기술 용어, 320px 폭, Android font scale을 검증한다.
- 색상 대비는 WCAG AA를 목표로 하며 상태를 색상만으로 구분하지 않는다.

## 12. 테스트 계획

### Frontend

- 구조화 요약 정상 렌더링.
- `summaryMeta`가 없는 레거시 데이터 fallback.
- keyPoints 0, 1, 3, 5개 렌더링.
- 긴 제목 3줄 제한과 긴 영문 줄바꿈.
- 복사 성공·실패·중복 탭.
- 원문 URL 없음과 `Linking.openURL` 실패.
- 더보기 메뉴 항목과 삭제 확인.
- `SUMMARIZING`, `SUMMARY_FAILED`, `CONTEXT_INSUFFICIENT` 상태별 UI.
- 200% 글자 확대 및 TalkBack/VoiceOver 탐색 순서.

현재 모바일 패키지에 테스트 러너가 없으므로 컴포넌트 테스트를 도입하려면 Jest와 React Native Testing Library 설정을 별도 작업으로 포함한다.

### Backend

- AI 응답 정규화: 빈 문자열, 5개 초과 항목, 잘못된 confidence.
- 요약 API DTO/JSON 호환성.
- 사용자 A가 사용자 B의 글 조회·재시도·삭제를 할 수 없는지 확인.
- 동일 article 재시도 동시 요청 시 카운트와 queue job 중복 방지.
- worker 재시도 순서 역전 시 오래된 결과가 덮어쓰지 않는지 확인.
- AI API timeout·429·5xx와 추출 실패 시 상태 전이 검증.
- 삭제와 worker 완료가 경쟁하는 시나리오.
- soft delete 도입 시 목록·홈·카운트에서 삭제 글 제외 및 restore 멱등성.

## 13. 구현 단계

### Phase 1 — 안전한 화면 개편

1. 상세 화면 컴포넌트 분리.
2. 구조화 요약 데이터 바인딩과 레거시 fallback.
3. 정보 구조·타이포그래피·여백 변경.
4. 복사 액션과 상태 피드백.

Backend API 변경 없이 배포할 수 있다.

4. 외부 API 실패 분류 및 테스트.

### Phase 3 — 복구 가능한 삭제

1. soft delete 정책과 DB migration.

3. restore API와 멱등성 테스트.
4. 프론트 실행 취소 토스트 연결.
5. 보존 기간 이후 hard-delete 정리 작업 검토.

## 14. QA 체크리스트와 완료 조건

- 첫 화면에서 제목, 한 줄 요약, 핵심 포인트가 원문 CTA보다 먼저 보인다.
- 한 줄 요약과 상세 요약이 동일 문자열로 중복 표시되지 않는다.
- 첫 화면에 Primary CTA는 하나만 존재한다.
- 분석 메타데이터가 제목보다 강하게 보이지 않는다.
- 핵심 포인트가 목록 구조로 표시되고 항목 사이가 명확히 구분된다.
- 최대 3개 대표 태그만 노출된다.
- 삭제는 더보기 메뉴의 최하단에 있고 확인 절차를 거친다.
- 서버 복구 계약 전에는 실행 취소가 가능한 것처럼 표시하지 않는다.
- 요약 생성 중·실패·맥락 부족·레거시 데이터 상태가 모두 깨지지 않는다.
- 44×44px 터치 영역, safe-area, 200% 글자 확대를 통과한다.
- 모바일 typecheck와 Backend 단위·통합 테스트가 통과한다.
- 변경 후 전체 diff에서 API 타입과 실제 응답 구조가 일치한다.
